# Translations

The kit translates some of its own text and nothing of yours. What it needs is one provider
and one Map; what it does without them is go blank. The provider's props, `getCommonTranslation`
and adding a language are on the site's
[Translation](https://api.onlyoffice.com/docspace/ui-kit/getting-started/translation.md) page.

## The Map

`TranslationProvider`'s `translations` prop is
`Map<language, Map<namespace, Record<string, string>>>`. The kit ships the tables it needs
inside the package:

```tsx
import type { ReactNode } from "react";
import { TranslationProvider } from "@onlyoffice/apps-ui-kit/providers/translation";
import common from "@onlyoffice/apps-ui-kit/locales/en/Common.json";

const translations = new Map([["en", new Map([["Common", common]])]]);

export function Translated({ children }: { children: ReactNode }) {
  return (
    <TranslationProvider locale="en" translations={translations}>
      {children}
    </TranslationProvider>
  );
}
```

**The package ships `en` and nothing else**, in three namespaces: `Common` (685 keys), which is
the only one the components read, and `Settings` and `Payments` beside it for the portal-internal
screens. There is no `locales/fr`, no `locales/de` — every other language is the application's to
supply, and saying so is half the answer when someone asks why a label is blank.

Add languages as entries in the outer Map and your own namespaces in the inner one. The
provider builds an i18next instance of its own rather than initialising the i18next singleton,
and that decides what does **not** fix a blank kit label: wrapping the app in
`I18nextProvider`, or calling `addResourceBundle` on the application's own i18next, fills the
application's instance and never reaches the kit's. Those are the first things an i18next user
reaches for, so say so when someone asks why a label is blank. The kit's tables reach it only
through this Map. The same separation is why an application already using i18next keeps its
own configuration, and why your `t()` and the kit's share nothing unless your namespace is in
the Map.

## What happens without it

`TranslationProvider` with no `translations` renders its children and installs no i18next
context at all. The kit's translated surfaces then come out **empty**, not as raw keys,
because the helper behind them returns `""` when it can find no instance. The console gets one
line per key:

```
[i18n] Missing translation for key "Common:Copy". Ensure the TranslationProvider is mounted
or window.i18n.loaded contains the required namespaces [Common].
```

Toasts arriving with no title line, blank tile menus and an unlabelled back button in `Article`
are all this. Eleven components translate a label of their own — `article`, `color-picker`,
`drop-down-item`, `file-input`, `filter`, `operations-progress-button`, `room-type`, `selector`,
`table`, `tiles`, `toast` — and nothing else in the kit does, so a component not on that list
showing nothing has some other cause.

## Which surfaces need it

Most of the kit takes its text from props and needs nothing. The ones that translate
themselves:

- **`toastr`** — the default titles, looked up at call time: `success` → `Done`, `error` →
  `Warning`, `warning` → `Alert`, `info` → `Info`. The middle two are crossed over, not a typo. Pass `null` as the title to suppress it deliberately rather than leaving it empty.
- **The tiles** — the three-dot menu and its tooltip.
- **`Article`'s back button**, and the portal-internal components generally, which is part of
  why they are portal-internal.

Each component page names its own dependency in the *Import* section, under the providers it
needs.

## Two ways in, one of them the portal's

The kit reads translations through two paths, and both fall back to `""`:

- `useTranslation("Common")` from `react-i18next`, served by the provider's instance;
- `getCommonTranslation(key)` from `utils/i18n`, which prefers `window.i18n` — the global the
  DocSpace client sets up — and falls back to the instance the provider registered.

An application of its own only ever uses the first path, through the provider. `window.i18n`
is the portal's and is not something to construct.

## Language and direction are two props

`locale` on `TranslationProvider` picks the language of the labels. `locale` on
`ThemeProvider` picks the writing direction and the font family. They are separate props on
separate providers and nothing keeps them in step — pass the same string to both.
