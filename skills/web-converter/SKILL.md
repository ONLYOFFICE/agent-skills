# ONLYOFFICE Web Converter API

Guidance for the **ONLYOFFICE Docs Conversion API**: converting a file from one format to another via a single HTTP call to the Document Server, with no editor session and no `config`/`editorConfig`/`events` payload involved. This file is the whole skill - the official docs below are the field by field source; **Core rules** is what they don't say explicitly: the ways a request or response fails *quietly*.

This is a standalone concern from embedding the Document Editor - a live editing session has its own contract (config payload, callback handler, Command Service) covered by the sibling **`doceditor`** skill, and generating a whole sample integration around it (whose `/convert` route defers back to this skill) is the sibling **`doceditor-integration`** skill's job. Reach for those when the task involves `DocsAPI.DocEditor` at all; reach for this one when it's purely "take file A, hand back file B". Generating a file that doesn't exist yet - from data, a template, a script - is the sibling **`web-builder`** skill (`/docbuilder`, a different request and response shape).

## How to use

1. Read [Request](https://api.teamlab.info/docs/docs-api/additional-api/conversion-api/request.md) for the request shape, then [Response](https://api.teamlab.info/docs/docs-api/additional-api/conversion-api/response.md) for parsing the result.
2. [Signature](https://api.teamlab.info/docs/docs-api/additional-api/signature.md) covers JWT signing the request when the Document Server has token auth enabled - the service reads the token from the JSON body's `token` field ("Token in body", the recommended vector) and falls back to an `Authorization: Bearer` header only when the body has none.
3. [Error codes](https://api.teamlab.info/docs/docs-api/additional-api/conversion-api/error-codes.md) and [Conversion tables](https://api.teamlab.info/docs/docs-api/additional-api/conversion-api/conversion-tables.md) are lookups: the negative error code table, and the supported pair matrix to check before sending a request.
4. **A detail these pages don't cover is a required lookup, not license to guess** - follow that page's own links, or [Basic concepts](https://api.teamlab.info/docs/docs-api/get-started/basic-concepts.md) generally, rather than filling a gap from memory.

## Definition of done

The request sends `filetype`, `key`, `outputtype`, and `url`, with the two type values lowercased and, when auth is enabled, every one of those parameters inside the signed token payload - preferably sent as the body's `token` field. The request goes to `/converter`, which answers in JSON; the legacy `/ConvertService.ashx` answers in XML unless the request sends `Accept: application/json`. Whether the pair is convertible at all is checked against the format table before the request goes out, never assumed or hand typed. When `async: true`, the caller re-polls the *identical* request under the *same* `key` until `endConvert: true`, bounded by a timeout or attempt cap; progress is shown as a state (converting/done), because `percent` is only ever `0` or `100`. The response's `error` key is checked before `fileUrl` is read, and every negative code maps to its own message or branch - `-7` (input error), `-8` (invalid token, never retried as-is), `-5` (password), and the rest - not a single generic "conversion failed" - and the codes that fail identically on every identical request never go back through a retry, the job queue's included.

## Core rules

These are the rules the pages above state as *fields*, not as *consequences* - what a wrong or missing one actually does, which is usually nothing you'd notice until it's in front of a user.

- **When you don't know, look it up - don't guess.** A field, error code, or format pair the pages above don't answer is a required live-docs check, not something to fill in from memory.
- `POST` to `https://documentserver/converter` with lowercase `filetype`/`outputtype`/`key`/`url`. `/converter` answers in JSON unless the request's `Accept` prefers XML; the legacy `/ConvertService.ashx` (still routed, still in old integrations) is the reverse - it answers in XML (`<FileResult><Error>...`) unless the request sends `Accept: application/json`, so a client there that calls `.json()` fails with a decode error pointing nowhere near the cause. Sending `Accept: application/json` is correct on both.
- **With JWT on, only what's inside the token counts.** By default (`tokenRequiredParams`) the service replaces the request's parameters with the token's decoded payload, so `filetype`, `outputtype`, `key`, `url`, `async`, `password` and the rest all belong *inside* the signed payload - a field sent in plain JSON next to the token is silently dropped (a `password` beside the token never reaches the converter, and the file fails as `-5`). The token is read from the body's `token` field - the vector the docs recommend - or, only when the body has none, from the `Authorization: Bearer` header (header name and prefix are server config, `services.CoAuthoring.token.inbox`); a header token signed over the full request works. Don't report a header token as a defect on its own; report a token that doesn't carry the parameters.
- With `async: true` the call returns immediately: re-poll the *identical* request under the *same* `key` until `endConvert: true` - a fresh key per attempt restarts the job from zero - and bound that loop with a timeout or attempt cap so a job the server gave up on doesn't hold a worker forever. `percent` is not progress: the server sends `0` on every intermediate response and `100` once `endConvert` is `true` (the Response page's `percent: 95` example notwithstanding - `fillResponse` computes `end ? 100 : 0`). A progress bar bound to it sits at zero and jumps to done; show a state (queued/converting/done) or elapsed time instead, and don't animate a synthetic percentage either.
- Check the pair against the format matrix before sending. The matrix is [`ONLYOFFICE/document-formats`](https://github.com/ONLYOFFICE/document-formats)' `onlyoffice-docs-formats.json` - the same file the Document Server reads - an array where a pair is supported when the entry whose `name` is the `filetype` lists the `outputtype` in its `convert` array. Pin it to the ref matching the Document Server in use (a `release/vX.Y.Z` branch or a commit hash) and use the whole file: in a generated integration, as a git submodule; in a one-off script with no repo around it, fetched from the pinned ref's raw URL once at preflight, or copied verbatim with the ref recorded next to it. Never hand-type the pairs, trim the file down to the pairs the task mentions, or re-fetch it per request - each of those drifts from what the server accepts, which is how a newly added format silently goes unsupported. Check `error` before reading `fileUrl`, keeping the negative codes distinct: `-7` (input error - what an illegal pair comes back as), `-8` (invalid token - will fail identically on every retry, so don't retry it), `-5` (incorrect password). All three read the same in a flat "conversion failed" and need different fixes.
- A report that says only "conversion error" is missing the one fact that would answer it - get the real `error` value logged (or read it directly if you're working from code) before reasoning any further; collapsing ten different codes into one string is usually the actual bug, not something to work around. When only the symptom is available and the code genuinely isn't, don't hand back the whole code table as a menu of equally-weighted guesses - commit to one diagnosis and say so, the way you'd name a root cause rather than list every suspect. A fixed, non-growing set of items failing identically on every retry while everything else succeeds first try rules out anything universal (a bad shared secret, a down server, misconfigured auth) and points at something specific to those items or their request; retrying, or disabling JWT to check, can't change a deterministic-per-request outcome and is wasted motion either way. Among item-specific causes, favor the mundane gap over the exotic one - a parameter some inputs need and others don't (a password, an explicit format hint, a size override) going unset for a subset of requests is a far more common bug than a subset of files being selectively corrupt or unreachable, and it's the one worth naming first. The same discipline applies to a contract deviation you actually find in code (a token signed over only some of the parameters, a fresh key per poll, `.json()` on the XML endpoint): state what it does under the setup described - it will fail once X is true - instead of softening a checkable consequence into "probably fine."
- All JWT signatures are HMAC-SHA256 (HS256), computed **server-side only** - never sign the token in frontend code. Load the signing secret from the environment and **fail startup if unset** - never hardcode a fallback in application source.
- Map every negative error code to its own branch or message in the generated code - a table in a doc page is documentation, not implementation. The branch has to decide retries too, and the decision has to reach wherever retries actually happen: `-3`, `-5`, `-7`, `-8`, `-9` and `-10` fail identically on an identical request, so retrying them as-is only delays the answer; `-1`, `-4` and `-6` can be transient; `-2` means move the job to `async`. A job queue (BullMQ `attempts`, Celery `autoretry_for`, a generic retry wrapper) retries every thrown error unless the permanent ones are marked unrecoverable - labelling `-8` `retryable: false` in an error object while the queue still retries it three times is the same bug as not labelling it.
- In an audit, report each independent cause as its own finding, even when several combine into one symptom - an unchecked `error` field and a loop with no bound are two fixes, and folding them into one lets the second survive the first's fix. Say explicitly which parts of the code are already correct, so the reader doesn't spend time on them.
- `url` has to be an address the Document Server itself can reach - not a local filesystem path, not a `localhost` URL that only resolves inside the calling process.
