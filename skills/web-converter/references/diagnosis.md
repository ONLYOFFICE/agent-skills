# Diagnosing and auditing conversion failures

Read this before answering a "conversion error" report or reviewing someone else's converter. The error codes themselves are in [errors.md](errors.md).

## Diagnosing from a report

A report that says only "conversion error" is missing the one fact that would answer it - get the real `error` value logged (or read it directly if you're working from code) before reasoning any further; collapsing ten different codes into one string is usually the actual bug, not something to work around. When only the symptom is available and the code genuinely isn't, don't hand back the whole code table as a menu of equally-weighted guesses - commit to one diagnosis and say so, the way you'd name a root cause rather than list every suspect. A fixed, non-growing set of items failing identically on every retry while everything else succeeds first try rules out anything universal (a bad shared secret, a down server, misconfigured auth) and points at something specific to those items or their request; retrying, or disabling JWT to check, can't change a deterministic-per-request outcome and is wasted motion either way. Among item-specific causes, favor the mundane gap over the exotic one - a parameter some inputs need and others don't (a password, an explicit format hint, a size override) going unset for a subset of requests is a far more common bug than a subset of files being selectively corrupt or unreachable, and it's the one worth naming first. Name it as *not sent*, and only that: when you haven't seen the request-building code, the diagnosis is that the request doesn't carry the parameter - don't add "or it's sent beside the token" as a second branch, since that is a claim about code nobody has shown you, and it's the branch that makes disabling JWT look like a fix. The fix you hand over is concrete: send the parameter (the file's `password`, from wherever the caller already records it per file) inside the signed payload, check `error` before reading `fileUrl`, and stop retrying the codes that fail identically. Disabling JWT is no test and no fix: a parameter that was never sent is still missing with JWT off, so the failure doesn't change - say so plainly. The same discipline applies to a contract deviation you actually find in code (a token signed over only some of the parameters, a fresh key per poll, `.json()` on the XML endpoint): state what it does under the setup described - it will fail once X is true - instead of softening a checkable consequence into "probably fine."

## Auditing code

In an audit, report each independent cause as its own finding, even when several combine into one symptom - an unchecked `error` field and a loop with no bound are two fixes, and folding them into one lets the second survive the first's fix. Say explicitly which parts of the code are already correct, so the reader doesn't spend time on them.
