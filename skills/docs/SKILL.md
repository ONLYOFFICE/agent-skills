# ONLYOFFICE Docs API

Knowledge base for integrating **ONLYOFFICE Docs API** (v8.2+): client-side editor embedding, the config payload it's built from, the server-to-server contracts (callback, Command Service, Conversion API), and the JWT signature scheme that ties them together. Built from the official docs at `api.onlyoffice.com/docs/docs-api/`.

## How to use

1. **Name the task shape first** (table below). The deliverable and the definition of done differ per shape, and mistaking one for another is how a build ships missing an endpoint nobody asked about out loud, or a review turns into a rewrite the user explicitly didn't want.
2. Start at [`api.md`](references/api.md) for the client bootstrap (script loading, `DocsAPI.DocEditor` constructor, iframe rules) — every other file delegates back to it as the entry point.
3. Reference the knowledge files below for exact field names, payload shapes, and constraints. Each file is self-sufficient — use its own rules and examples rather than the linked live docs.
4. **A detail this knowledge base doesn't cover is a required lookup, not license to guess.** When a task needs a field, edge case, error code, or schema shape that isn't in the file you're reading, that file's own live-docs link (its "Documentation Query Rules" -> Fallback line) — or, for vendored data, the vendored source itself (the format table, the templates repo) — has to be checked before you write code that depends on the answer. A plausible-but-unverified value shipped here is exactly the "hallucinated surface" failure [`api-testing.md`](references/api-testing.md)'s Phase 1 exists to catch, and it fails silently until something actually exercises that exact path. This applies whether or not the task otherwise "feels" complete — an unusual combination of requirements (an uncommon target language, a demanding UI brief, a rare permission or mode) is precisely when a gap in memory is most likely and least likely to be noticed. The only exception: don't fetch a live page to re-confirm something the reference file you're already working from already states — that's needless, not thorough.

### Definition of done (build shape)

The four server endpoints are mounted and reachable — callback, download, upload, **and convert even when nothing in the demo calls it** — with the embedding page as the separable fifth. `document.key` rotates on every save and is persisted beside the file; `documentType` comes from the extension family; `callbackUrl`/`user` sit under `editorConfig` and handlers under `events`; every token is signed server-side; the callback verifies before it fetches anything and answers exactly `{"error": 0}` for what it handled; conversion sends `Accept: application/json` with lowercase types, a body token, and a **bounded** async poll; which formats are supported comes from the vendored format table and blank/seed files from vendored templates, never from a hand-typed list; and any UI meets [`ui.md`](references/ui.md)'s bar — including the named style's real collection layout (cards vs table) when one was named. Whenever the deliverable has a file list/dashboard page, `editorConfig.customization.goback` points at it and `onRequestClose` actually navigates back there — closing the editor is not done until the visitor lands back on the dashboard, not a blank page. When the request includes version history / comparison / restore, the history store (increment, actor, snapshot, **content hash**) and **both** `onRequestHistory`→`refreshHistory` (the list) and `onRequestHistoryData`→`setHistoryData` (opening one version's diff — a distinct event pair, not `onRequestRestore`) are required, not an optional extra — a build with only the first wired shows a populated history list where every entry silently fails to open. See [`example.md`](references/example.md) and [`methods.md`](references/methods.md). JWT and other production secrets come from the environment with **no hardcoded fallback in source** — fail fast if unset ([`infrastructure/compose.md`](references/infrastructure/compose.md)). Every one of those gets its own test per [`api-testing.md`](references/api-testing.md)'s Coverage Mandate — a piece with no test is not done, and a capability that exists only as an internal function call is not mounted.

## Core rules (always apply)

- **When you don't know, look it up — don't guess.** If a field, error code, mode value, or schema shape isn't answered by the reference file routed to for this task, that file's live-docs link (or the vendored source it points at) is a required check, not an optional one — see "How to use" step 4. This is most likely to matter, and most likely to be skipped, exactly when a request stacks unusual requirements (an uncommon target language, a demanding design brief, a rarely-used permission or config axis) that crowd out double-checking the less-familiar parts.
- Load the API script from the Document Server origin, then call `new DocsAPI.DocEditor(id, config)`. Init **replaces** the container element with a sandboxed iframe — size a wrapper element around it, not the placeholder itself; talk to the frame only through `methods` and `events`.
- Whenever this deliverable has a file list/dashboard page, wire `editorConfig.customization.goback` to point at it (`requestClose: true`) and make `onRequestClose` actually navigate back there after `destroyEditor()` — not just close the tab or stop at a blank page. An editor with no way back is a dead end, not a demo. See [`configuration/editor.md`](references/configuration/editor.md) and [`configuration/events.md`](references/configuration/events.md).
- `config.document` and `config.documentType` are required; `documentType` must match `document.fileType`'s family (`docx`->`word`, `xlsx`->`cell`, `pptx`->`slide`, `pdf`->`pdf`). Don't put `callbackUrl`, `lang`, or event handlers at the config root — they belong in `editorConfig`/`events`.
- `document.fileType`, `key`, `title`, `url` are all required. Update `key` on every save — reusing a stale key across an updated file causes visual corruption and out-of-sync revisions.
- `editorConfig.callbackUrl` and `editorConfig.user.{id, name}` are required for a working integration. `user.id` must be an anonymized session identifier — never a plaintext email or real name.
- Implement `onDocumentReady` and `onDocumentStateChange` at minimum. State-changing methods (`refreshHistory`, `insertImage`, `setHistoryData`, …) must be called from inside or right after their matching event handler.
- Your `callbackUrl` handler answers exactly `{"error": 0}` for every callback it handled — **including the statuses it only logs** — or the editing service reads the reply as a failed delivery and retries that same callback forever. Two exceptions matter as much as the rule: a request whose token doesn't verify is rejected *without* that acknowledgement (acknowledging a forgery tells the sender it worked), and a genuine internal failure — download failed, disk write failed — answers non-zero so the retry does its job instead of silently losing the user's save. Verify the token *before* fetching anything from `url`, branch every `status` (`2` save and `6` force-save both download and persist; `6` leaves the session open), and don't read `url` unguarded — it's absent on `1` and `4`. See [`callback/handler.md`](references/callback/handler.md).
- All JWT signatures are HMAC-SHA256 (HS256), computed **server-side only** — never sign tokens in frontend code, that exposes the secret in cleartext browser bundles. Load `JWT_SECRET` (and any session/proxy secrets) from the environment and **fail startup if unset** — never hardcode an `envOr`/`getenv` fallback like `"change-me-…"` in application source; placeholders belong only in `.env.example` ([`infrastructure/compose.md`](references/infrastructure/compose.md)).
- Three token placements, pick by caller: root `token` in the config payload signs the whole object for `DocsAPI.DocEditor` (browser); a `token` key inside an HTTP JSON body is used by the Command Service, the Conversion API request, and the callback outbox; an `Authorization: Bearer <jwt>` header wraps its claims under `payload`.
- When the request includes version history, comparison, or restore: persist each revision with an incremented number, actor, snapshot, and a **content hash** of the saved bytes (computed on callback save/force-save), and wire **both** history event pairs — `onRequestHistory` → `refreshHistory` (populates the list) **and** `onRequestHistoryData` → `setHistoryData` (opens one version's diff; a distinct event from `onRequestRestore`, which reverts content). Wiring only the first leaves every entry in a populated list silently unable to open — the "history doesn't work" symptom with no server-side error to chase. Download and persist the callback's `changesurl` yourself rather than re-serving Document Server's own transient cache link, and keep every past revision's bytes independently fetchable by its own key, not just the current one. There is no static config `history` field ([`methods.md`](references/methods.md), [`configuration/events.md`](references/configuration/events.md)).
- Command Service: `POST /command` with a `c` value (`forcesave`, `info`, `drop`, `meta`, `version`), wrapped in a signed `token` when JWT is enabled. Error `4` = no changes to force-save; `6` = invalid token signature.
- Conversion API: `POST /ConvertService.ashx` with lowercase `filetype`/`key`/`outputtype`/`url`, the token inside the JSON body, **and an `Accept: application/json` request header** — without it the service replies in XML (`<FileResult><Error>...`) and the failure surfaces as a JSON decode error pointing nowhere near the cause. With `async: true` the call returns immediately: re-poll the *identical* request under the *same* `key` until `endConvert: true` (a fresh key per attempt restarts the job from zero), and bound that loop with a timeout or attempt cap so a job the server gave up on doesn't hold a worker forever. The response's own `percent` is real progress — render it rather than animating something synthetic. Check the pair against the vendored format matrix ([`table.md`](references/additional/conversion/table.md)) before sending, and check `error` before reading `fileUrl`, keeping the negative codes distinct: `-7` (input error — what an illegal pair comes back as), `-8` (invalid token — will fail identically on every retry, so don't retry it), `-5` (incorrect password). All three read the same in a flat "conversion failed" and need different fixes.
- Wherever a response carries a small set of named error/status codes (conversion's `-1`…`-10`, Command Service's `1`/`2`/`3`/`4`/`6`, the callback's `status`), map every value to its own branch or message in the generated code — a table in a reference file is documentation, not implementation. Preserving the raw integer in a log line and funneling everything else into one generic "failed" branch throws away the distinction the table exists for; see the worked map/switch in [`errors.md`](references/additional/conversion/errors.md), [`command.md`](references/additional/command.md), and [`callback/handler.md`](references/callback/handler.md) for the pattern to follow.
- The endpoint surface is four server endpoints plus a separable page. The callback receiver (`POST /track`), download (`GET /download`), upload (`POST /upload`) and conversion (`POST /convert`) are the contract a third-party integrates against, so **all four get mounted even when the deliverable's own UI never calls one of them** — conversion reachable only as an internal step inside the upload handler is a capability, not the endpoint, and an integrator has no way to convert on demand. The embedding page (`GET /`) is the fifth and the only optional one, kept removable per [`infrastructure/backend.md`](references/infrastructure/backend.md).
