# ONLYOFFICE Web Builder API

Guidance for the **ONLYOFFICE Docs Document Builder API**: generating one or more files by having the Document Server run a `.js` builder script, via a single HTTP endpoint, with no editor session and no `config`/`editorConfig`/`events` payload involved. The official docs below are the field by field source; **Core rules** is what they don't say explicitly: the ways a request, a script or a response fails *quietly*. Detail that only some tasks need is in `references/`, routed from **References** below.

This is a standalone concern from its siblings. Turning an *existing* file into another format is the **`web-converter`** skill (`/converter`, a different request and response shape - don't carry its habits over, see below). A live editing session is the **`doceditor`** skill, and generating a whole sample integration around the editor is **`doceditor-integration`**. Reach for this one when the task is "run this script, hand back the files it made".

## How to use

1. Read [Document Builder API](https://api.onlyoffice.com/docs/docs-api/additional-api/document-builder-api.md) - the request and response fields, the async/sync/token/argument/multi-output/compare examples, and the error code table, all on one page.
2. [Token in body - Document builder](https://api.onlyoffice.com/docs/docs-api/additional-api/signature/request/token-in-body.md#document-builder) covers JWT signing the request when the Document Server has token auth enabled.
3. The script itself: [Script file](https://api.onlyoffice.com/docs/document-builder/using-cli/script-file.md) for its structure and syntax rules, [builder vs builderJS](https://api.onlyoffice.com/docs/document-builder/using-cli/overview.md#builder-vs-builderjs), [command line arguments](https://api.onlyoffice.com/docs/document-builder/using-cli/command-line-arguments.md) for the global `Argument` object the request's `argument` lands in, and the [Office JavaScript API](https://api.onlyoffice.com/docs/office-api/get-started/overview.md) for the `Api.*` calls that build content.
4. **A detail these pages don't cover is a required lookup, not license to guess** - follow that page's own links, the [Document Builder index](https://api.onlyoffice.com/docs/document-builder/llms.txt), or [Basic concepts](https://api.onlyoffice.com/docs/docs-api/get-started/basic-concepts.md) generally, rather than filling a gap from memory. That goes double for Office API method names in the script: a misspelled or invented method fails the whole generation with `-3`.

## Definition of done

The request `POST`s to `https://documentserver/docbuilder` with `url` pointing at a script the Document Server can fetch and the caller controls, and with request-specific data sent as `argument` (read in the script as the global `Argument`) - never string-interpolated into the script source. With JWT on, every request - the first one *and* each poll - carries its own token signed over *all* of that request's parameters. When `async: true`, the first request omits `key` (or sends a fresh, never used one), the `key` is taken from the first response, and each poll sends `{async: true, key}` without `url`, bounded by a timeout or attempt cap; there is no `percent` to show, so progress is a state (queued/generating/done), not a number. `error` is checked before `end`/`urls` is read, every documented code (`-1`, `-2`, `-3`, `-4`, `-6`, `-8`) maps to its own branch or message - with `-3` and `-8` never going back through a retry, the job queue's included - and the `urls` entries - one per `SaveFile` in the script, keyed by the file name it was saved under - are downloaded promptly into the app's own storage rather than handed out as permanent links.

## Core rules

These are the rules the pages above state as *fields*, not as *consequences* - what a wrong or missing one actually does, which is usually nothing you'd notice until it's in front of a user.

- **When you don't know, look it up - don't guess.** A request field, an error code, or an Office API method the pages above don't answer is a required live-docs check, not something to fill in from memory.
- **The builder is not the converter - don't port its polling habits.** The two share a server and a JWT scheme and nothing else: the converter's client picks `key` and re-sends the identical request; the builder's `key` comes *back* from the first async response and every poll is `{async: true, key}`. A poll that re-sends `url` without the returned `key` doesn't read the job's status - it queues a brand-new generation under a new server-minted key, every time, so the loop never sees `end: true` and the server fills up with orphaned jobs. The response fields differ too: `end` (not `endConvert`), `urls` - an object keyed by output file name (not a single `fileUrl`) - and **no `percent` at all**. A progress bar can show queued/generating/done or elapsed time; animating a number the service never sent is inventing data.
- A caller-supplied `key` is accepted, but it's the job's identity: the service stores results by key, so reusing a key from an earlier job returns *that* job's stale output instead of running the new script. Either omit it and use the returned one, or mint a fresh one per job.
- **With JWT on, only what's inside the token counts.** By default (`tokenRequiredParams`) the service replaces the request's parameters with the token's decoded payload, so `url`, `async`, `key` and `argument` all have to be *inside* the signed payload - a field sent in plain JSON next to the token is silently dropped (an `argument` beside the token arrives in the script as nothing; an `async` beside it makes the call blocking). Apply this to parameters the code actually sends - when only a symptom is described, don't assume how the request was built. Each poll is its own request and needs its own token signed over `{async: true, key}`. HS256, signed **server side only** with the secret loaded from the environment, **startup fails if it's unset** - no hardcoded fallback. `-8` (invalid or expired token) fails identically on every retry; don't retry it.
- **The script is code the Document Server executes - treat it that way.** Its `url` is a file the caller hosts and controls (a static asset of the app, a known template), never a URL supplied by an end user. Request data goes in `argument` and is read as `Argument["name"]` in the script; building the script by concatenating user input into JavaScript source is script injection, and a stray quote in a customer name breaks the generation with `-3` long before it becomes a security incident. A static script plus `argument` also means one reviewed script instead of one per request.
- Every URL the service fetches has to be reachable *from the Document Server*: the script `url`, and any `builderJS.OpenFile(...)`/`OpenTmpFile(...)` inside the script (absolute URL, never a local path). A `localhost` address or a path on the calling machine fails as `-4` (download error) or `-3`, not as anything that names the URL. So the base address the script is served from is configuration that fails startup when unset, exactly like the secret - a `localhost` default works on the developer's machine and nowhere else.
- Script syntax fails as `-3` with no line number in the response, so read [references/script.md](references/script.md) before writing one: the three-part structure with one open file at a time, `builderJS` when the script uses JavaScript variables, Office API signatures that changed between server versions (`Api.CreateTable` swapped its arguments in 9.4.0), and every `SaveFile(format, name)` becoming one `urls` entry under exactly that `name`.
- `urls` are temporary signed links into the Document Server's cache - download each file into the app's own storage when `end` is `true`, rather than storing the link or handing it to a user to open later.
- Check `error` before `end`/`urls`: an error response is `{"error": -N}` with no `end` and no `key`, so a loop that only tests `end` spins until its own cap. Map each documented code (`-1`, `-2`, `-3`, `-4`, `-6`, `-8`) to its own branch, and let the branch decide retries wherever retries actually happen - `-3` and `-8` are permanent, the job queue's `attempts` included. What each code means and the retry class: [references/errors.md](references/errors.md).
- In an audit, report each independent cause as its own finding, even when several combine into one symptom - an unchecked `error` field and a loop with no bound are two fixes, and folding them into one lets the second survive the first's fix. Data spliced into script source is two findings in one: a script that breaks on a quote (`-3`) *and* script injection into code the Document Server runs - name both, and name the fix (one static script, the data in `argument`, read as `Argument`), not just escaping. Say explicitly which parts of the code are already correct. The script rules an audit checks against are in [references/script.md](references/script.md), the codes in [references/errors.md](references/errors.md).
- `async: false` holds the HTTP call open until the whole script finishes - fine for a one-page letter, wrong for a hundred-page report or a request thread that can't block; use `async: true` there. Since 8.1, add `?shardkey=<key>` to the query string of requests that carry a key; on a sharded cluster an async request without it is quietly downgraded to a blocking one.
