# ONLYOFFICE Document Editor Integration Examples

Knowledge base for **generating a whole ONLYOFFICE Document Editor integration from scratch**: project scaffolding, the backend vs UI scope decision, a UI built on `docspace-ui-kit-react` (or the official framework component), Docker/nginx/compose infrastructure, hexagonal architecture, vendored template and format-table sourcing, and the testing methodology for the result. Built from the official Node.js sample app and ONLYOFFICE's own template/format repos.

This skill assembles a sample **around** the editor's own API contract rather than re-deriving it - every piece it scaffolds (the config object, the callback handler, JWT signing, the Command Service call) is built per the sibling **[`doceditor`](../doceditor/README.md)** skill's files, and a generated `/convert` route is built per the sibling **[`web-converter`](../web-converter/README.md)** skill's. All three ship together in the `onlyoffice` plugin. Reach for *this* skill when the task is "build me something," not "wire the editor into what we already have" (that's `doceditor` on its own) or "just convert this file" (that's `web-converter` on its own).

## How to use

1. Confirm the scope first with [`infrastructure/backend.md`](references/infrastructure/backend.md) - a reusable backend by default, a sample UI only when actually asked for.
2. Copy the starting point from [`templates/`](templates/README.md) - the language-neutral project skeleton, endpoint contract, and infra boilerplate - instead of freehand authoring them.
3. Build the endpoint surface per [`example.md`](references/example.md), the structure per [`architecture/hexagonal.md`](references/architecture/hexagonal.md), and each piece's actual contract from the sibling `doceditor` skill (config/signature/callback/command) and, for `/convert`, the sibling `web-converter` skill.
4. If there's a UI, [`ui.md`](references/ui.md) is the design bar - always built on [`dependencies/kit.md`](references/dependencies/kit.md)'s `docspace-ui-kit-react` regardless of requested style, or the official component for the editor mount itself in [React](https://api.onlyoffice.com/docs/docs-api/get-started/frontend-frameworks/react.md), [Angular](https://api.onlyoffice.com/docs/docs-api/get-started/frontend-frameworks/angular.md), or [Vue](https://api.onlyoffice.com/docs/docs-api/get-started/frontend-frameworks/vue.md).
5. Run [`example-checklist.md`](references/example-checklist.md) as a closing verification pass, then [`api-testing.md`](references/api-testing.md) for the testing methodology - one test per generated feature/step, run immediately after each change, not batched.
6. **A detail this knowledge base doesn't cover is a required lookup, not license to guess** - that file's own live docs link, or the vendored source it points at (the format table, the templates repo), has to be checked before writing code that depends on the answer. This is most likely to matter, and most likely to be skipped, exactly when a request stacks unusual requirements (an uncommon target language, a demanding UI brief, a rare permission or mode).

## Definition of done

The five backend endpoints are mounted and reachable with the demo module compiled out - the embedding page, callback, download, upload, **and convert even when nothing in the demo calls it** (built per the `web-converter` skill's contract). The demo dashboard - the file list and the list/create/rename/delete routes only it calls - is the separable part, and a build without it is actually run. Every field/handler/status the sibling `doceditor` skill's own Definition of Done requires (key rotation, config shape, JWT, the callback's exact `{"error": 0}`, the history event pair when in scope) holds for each generated piece - this skill doesn't restate that bar, it builds to it. Blank/seed files come from vendored templates and supported-format pairs from the vendored format table, never a hand-typed list. Any UI passes [`example-checklist.md`](references/example-checklist.md)'s §7 UI Bar checklist **in full** before being called done - including having actually asked, not assumed, the style/brand, collection-layout, and overall-shape questions [`ui.md`](references/ui.md) requires, and having built on `docspace-ui-kit-react` regardless of the answers. "Meets `ui.md`'s bar" means that checklist passing, not a read-through of the file followed by a self-assessment. Every output adapter is swappable, not a foundation: whatever cheap/demo implementation sits behind a port - an in-memory store, a stub gateway, a fake clock - sits entirely behind that port, so replacing it with a real one is one new adapter plus a composition-root wiring change, never a change to domain/use-case code ([`architecture/hexagonal.md`](references/architecture/hexagonal.md)'s "Swappable Adapters"). Every one of those gets its own test per [`api-testing.md`](references/api-testing.md)'s Coverage Mandate — a piece with no test is not done, and a capability that exists only as an internal function call is not mounted.

## Core rules

- **When you don't know, look it up - don't guess.** If a field, error code, mode value, or schema shape isn't answered by the reference file routed to for this task, that file's live-docs link (or the vendored source it points at) is a required check, not an optional one.
- **Generate the backend by default; keep the demo dashboard removable, not entangled.** The reusable API surface a third-party would actually call is the deliverable unless told otherwise; a demo dashboard sits behind its own module/build tag/feature flag so the backend still compiles and serves with it fully absent, not just unrouted.
- **The backend is five endpoints; the dashboard is everything else.** The embedding page (`GET /editor?file=…`, the page that builds the signed config and constructs `DocsAPI.DocEditor` for one file), the callback receiver (`POST /callback`), download (`GET /download`), upload (`POST /upload`) and conversion (`POST /convert`, built per the `web-converter` skill's contract) are the contract a third-party integrates against - an integrator links or iframes the embedding page for a file it already knows - so **all five get mounted even when the deliverable's own UI never calls one of them**, and conversion reachable only as an internal step inside the upload handler is a capability, not the endpoint. The demo dashboard is the file list page plus the list/create-new/rename/delete routes only it calls, and that whole bundle is what goes behind the flag. The split is by audience, not by "is it HTML": an integrator needs the editor page and never the file browser, so putting the editor page on the removable side, or the list/rename/delete routes on the backend side, gets it backwards.
- **Every field/handler this scaffolding wires up follows the sibling `doceditor` skill's own contract** - `document.key` rotation, `documentType`'s family match, `editorConfig`/`events` placement, the callback's exact `{"error": 0}`, both history event pairs when in scope. This skill decides *what* gets built and *how it's structured*; `doceditor` is the authority on whether each piece is correct.
- **Style it deliberately.** Whatever UI gets built is held to `ui.md`'s bar: always built on `docspace-ui-kit-react` (or the official framework component for the editor mount itself), one design system settled before the first component, and no part left as bare unstyled markup because it wasn't in the reference started from.
- **Blank/seed files and supported-format pairs are vendored, never hand-typed.** [`templates.md`](references/templates.md) for per-format "create new"/"sample" files, the `web-converter` skill's vendored `document-formats` submodule for which pairs actually convert.
- **JWT and other production secrets come from the environment with no hardcoded fallback in source** - fail startup if unset ([`infrastructure/compose.md`](references/infrastructure/compose.md)).
- **Every output adapter is swappable, not a foundation** - an in-memory store, a stub gateway, a fake clock sits entirely behind its port ([`architecture/hexagonal.md`](references/architecture/hexagonal.md)'s "Swappable Adapters"), and every generated feature/step gets its own test, run immediately after each change ([`api-testing.md`](references/api-testing.md)).
