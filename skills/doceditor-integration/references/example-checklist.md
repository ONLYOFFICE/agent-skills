# Integration example checklist
 
## Context & Purpose
 
A language-agnostic verification checklist for generating an ONLYOFFICE integration sample (backend, or backend + sample UI per [`infrastructure/backend.md`](infrastructure/backend.md)) in *any* target language - Rust, Python, Java, Go, PHP, whatever the user asked for. [`example.md`](./example.md) is the *content* reference (what the official Node.js example builds); this file is the *process* - every item below is something that actually broke a real generation session before it was added here.
 
**Do not check these boxes.** This file is a shared template, read fresh every session - ticking a box here persists nothing useful and corrupts the next session's copy. Track progress on a specific generation task in your memory system instead (a `project` memory noting which items were verified and which are still open), linked back to `[[example-checklist]]`.
 
## Reference Documentation Map
 
* **Content reference:** [`example.md`](./example.md) - the five endpoints and the sample UI's reference shape.
* **Applies alongside:** [`architecture/hexagonal.md`](architecture/hexagonal.md) (structure), [`infrastructure/backend.md`](infrastructure/backend.md) (backend-vs-UI scoping).
* **Testing methodology (after generation, and on every regeneration):** [`api-testing.md`](./api-testing.md) - this file's checklist runs *during* generation; that guide's phases run *after*, one test per feature/step, executed immediately following each change rather than batched at the end.

## Documentation Query Rules
 
* **Baseline:** This guide is self-sufficient - a process checklist, not a wrapped API. A bare filename below with no path (`api.md`, `configuration/events.md`, `methods.md`) is the sibling **`doceditor`** skill's file, not one in this directory.
* **Fallback:** None. An item missing below that caused a real bug is a gap worth adding, not a reason to skip verification.

## 1. Environment
 
- [ ] 1.1 The Document Server target answers a health check right now - not "it was reachable earlier" or "I started a container at some point." A local container can die silently (OOM, e.g.) between sessions; re-check its current status (`docker ps -a`) rather than trusting past state.
- [ ] 1.1a The deliverable brings up a reachable Document Server itself: one documented command (`make up`) on a machine with nothing running starts one per [`infrastructure/compose.md`](infrastructure/compose.md)'s "MAKING DOCUMENT SERVER REACHABLE LOCALLY", and reuses one already answering - even when the user said theirs is running. Checked in both directions with requests: the public URL's `/healthcheck` and `api.js` from the host, and the backend's health route from inside the documentserver container. The host alias for a natively-run backend is chosen per Docker runtime (Docker Desktop, Linux, Colima/Lima, Podman), never assumed to be `host.docker.internal`.
- [ ] 1.2 If a local, pinned checkout of `document-server-integration` exists on disk, it's diffed against in preference to fetching a remote branch. Branches drift, and a local checkout is frequently a *different* (often newer) revision than `main` - with different icon filenames, different markup for the same feature, or scripts the fetched branch doesn't have. If unsure which the user means, diff both rather than assuming they match.

## 2. Asset Fidelity (CSS/JS/images reused)
 
- [ ] 2.1 Every reused file is byte-diffed against the reference's own pinned revision - not hand-transcribed or "recreated from the gist of it." A hand-transcription silently drops or reorders declarations in ways that only surface as layout bugs much later.
- [ ] 2.2 Every icon/asset filename is verified against what the reference markup actually references, not assumed from what it "should" be named. A similarly-named file in a *different* feature's asset set (e.g. a WOPI-flavored icon variant sitting next to the non-WOPI one) is a different file for a different purpose.
- [ ] 2.3 The DOM structure is ported exactly per conditional branch when porting markup generated by a template language (EJS/Jinja/etc.) alongside CSS reused verbatim - not just the class names. Fixed-width flexbox/grid siblings only line up if every row/cell emits the same count and order of elements, populated or left empty, as every branch in the original template.
- [ ] 2.4 Numeric layout constraints that live only in the reference's *JS config* (a modal/dialog library's configured width, position, or breakpoint) are ported alongside the CSS - these are easy to miss entirely because they were never in a stylesheet to begin with.
- [ ] 2.5 Every component with no counterpart in the reused reference (added fresh for this generation, not ported from `index.ejs`/`jscript.js`) is actually styled - checked by name, not assumed covered because "most of the page looks fine." The direction it follows and where its values come from are [`ui.md`](./ui.md)'s call; §7 below is where that gets verified.

## 3. Comments in Generated Code
 
- [ ] 3.1 Every comment added or edited is re-read for a token that accidentally closes it early - most commonly in CSS, where citing two class names back-to-back (`.foo*/.bar`) produces a literal `*/` that terminates the comment mid-sentence. This is invisible on a read-through (the comment *looks* fine) and silently invalidates the entire next rule, identically in every browser, with no error most people will see. The same care applies to any language's own comment-closing sequence when a comment quotes code that might contain one (`-->` in HTML/XML, `*)` in OCaml-family languages, etc.).

## 4. Verification
 
- [ ] 4.1 CSS is run through an actual parser (not eyeballed, not brace-counted by hand) with zero parse errors, before considering a stylesheet change complete. A single malformed rule is dropped silently - most browsers give no visible error for it by default.
- [ ] 4.2 Endpoints are curled and their response shape/status/headers compared to what the reference implementation's equivalent does for the same input - including headers not obviously required (see §5).
- [ ] 4.3 When no real browser is available, the actual shipped script is run through a headless DOM (e.g. jsdom) with mocked `fetch`, to catch runtime errors and confirm state transitions happen. This is real signal but is *not* proof of visual rendering - a script can run flawlessly end-to-end and still be invisible on screen for a pure-CSS reason no JS simulation can see.
- [ ] 4.4 The user is asked what they visually observe only after 4.1-4.3, not instead of them. A pasted DOM snapshot is strong evidence of what the JS *did* (inline styles it set, classes it toggled) - it is not proof of what was visually *rendered*; the CSS rule meant to make an element visible may never have parsed at all (see 4.1).
- [ ] 4.5 Every buildable component is actually built with its real toolchain - `cabal build`/`stack build`, `npm run build`/`tsc --noEmit`, `go build`, `cargo build`, `docker build`/`docker compose build` for every Dockerfile and compose service - not read through and judged correct by eye. A read-through cannot see a hallucinated import, a type error, or a malformed Dockerfile the way the real compiler/builder does, and those are free to catch here versus discovered later as a runtime failure. If the sandbox genuinely has no toolchain available for a language, that gap is reported to the user explicitly as an unverified component - never silently treated as equivalent to a build that ran and passed.
- [ ] 4.6 Manual deployment, full cycle: every service is started directly with its native tooling - no containers - (`stack run`/`cabal run` the backend, `npm run dev` or `npm run build && npm run preview` the frontend), and one complete real cycle is driven through the running app end to end: register/log in -> reach the dashboard -> create or upload a file -> open it in the editor -> edit and save -> close and confirm it lands back on the dashboard (not a blank page) -> reopen and confirm the edit persisted. This is the cheapest full E2E because there's no orchestration or networking layer to mask a wiring bug between frontend and backend — a failure here is in the application code itself, not the deployment story.
- [ ] 4.7 Docker deployment, full cycle: when a docker-compose file (or equivalent multi-service orchestration) exists, `docker compose build && docker compose up -d`, wait for every service to reach a `healthy` status (not merely `running` - a container that crash-loops or never passes its health check is a shipped defect), then drive the *same* full cycle as 4.6 but through the containerized stack's actual public entrypoint (the reverse proxy), never a service's internal port directly. Passing 4.6 but failing here means the application works but the containerization/networking/proxy config doesn't - a distinct failure class worth its own check, not assumed covered by 4.6. While it's up, also confirm named volumes survive a `down`/`up` cycle (write a marker before `down`, check it's still there after `up`) rather than trusting the compose file's `volumes:` block on sight.

## 5. Protocol-Level Gotchas
 
- [ ] 5.1 Every header a reference implementation's HTTP client sends is captured, not just `Content-Type`. A reference implementation's own HTTP client/framework may set an `Accept` header implicitly that changes the server's response format entirely (e.g. ONLYOFFICE's Conversion API replies in XML by default and only switches to JSON given `Accept: application/json` - see the sibling `web-converter` skill). Missing this produces a response your own client can't parse, surfacing as a generic deserialization failure that looks unrelated to the real cause.

## 6. Backend Contract Discipline
 
- [ ] 6.1 A sample-UI-only feature (e.g. a live-progress poll for a conversion) is added via a new, additive endpoint rather than by changing an existing core endpoint's response shape or blocking/async behavior. A real third-party integrator may depend on the original, simpler contract.
- [ ] 6.2 Every value in a reused capability/format table is checked, not just the ones already wired up. A table can carry a signal your own code hasn't acted on yet (e.g. an `"auto-convert"` action meaning "silently convert before offering edit," separate from `"edit"` itself) - skipping it produces a feature gap that looks like a missing feature rather than an unread field.
- [ ] 6.3 Every endpoint on the contract surface is *mounted*, not merely implemented - the router itself is read and the embedding page, callback, download, upload and convert routes are each found on it, including the ones this deliverable's own UI never calls. The recurring miss is conversion: written correctly as an internal step inside the upload handler for the legacy auto-convert path, and never exposed as a route, so an integrator has no way to convert on demand. See [`example.md`](./example.md)'s Endpoints.
- [ ] 6.4 When the request includes version history, comparison, or restore: each saved revision stores an incremented version number, actor, snapshot/`changesurl`, and a **content hash of the saved bytes**; `onRequestHistory` calls `refreshHistory` (not a log-only stub); **`onRequestHistoryData` calls `setHistoryData` with the full documented object** — `fileType`, `key`, `url`, `version`, plus `changesUrl` and `previous{fileType, key, url}` whenever this isn't the first revision, plus the signed root/browser-vector `token` - not just `{key, url, version}`, which is the shape that throws inside Document Server's own bundle (`canUseHistory` of undefined) rather than erroring server-side; each revision's snapshot path is verified to actually be its own (open version N-1 after N exists and confirm the bytes differ from the live file, not just that the metadata row differs); restore is wired. A version list without hashes, a history panel that never gets `refreshHistory`, or a `setHistoryData` call missing any of the fields above is incomplete - see `methods.md`, `configuration/events.md`, and the sibling `doceditor` skill's Core rules and fault catalogue.
- [ ] 6.5 JWT / session / proxy secrets are read from the environment and the process **fails at startup if they are unset**. No `envOr("JWT_SECRET", "change-me-...")` (or language equivalent) appears in application source - placeholders live only in `.env.example`. See [`infrastructure/compose.md`](./infrastructure/compose.md).
- [ ] 6.6 A UI/demo page claimed to be "removable" (per [`infrastructure/backend.md`](infrastructure/backend.md)) is proven removable, not assumed: actually build/run the backend with the UI's package, module, build tag, or flag excluded, and confirm all five contract endpoints - the embedding page included - still compile and serve, while the dashboard's list/create-new/rename/delete routes are gone (a request to them 404s in that build). Sorting the demo-page handlers into their own files is not separation by itself - the *router/registration point* is what has to be conditional, and a README line calling it "optional" is not a substitute for one build that actually excludes it and still works.
- [ ] 6.7 Every format a "create new" / export UI *offers* (a hand-typed supported-formats list feeding button rendering) is cross-checked against what's actually vendored on disk for that exact format ([`templates.md`](./templates.md)). The offered-formats list and the vendored file set are two independent things that silently drift the moment one is edited without the other - a format present in one and missing from the other ships a button that fails the moment someone actually clicks it. Derive the offered list from what's actually present, or assert the two match at startup and fail loudly on a mismatch, rather than trusting that they still agree.
- [ ] 6.8 Every output adapter (repository, storage, gateway, signer, clock - whatever ports this deliverable has) is checked for swappability, not assumed from having followed the pattern: grep confirms nothing outside that one adapter's own folder imports its concrete type, and the composition root is the single place that decides which implementation is wired in. See [`architecture/hexagonal.md`](architecture/hexagonal.md)'s "Swappable Adapters" and [`templates/structure.md`](../templates/structure.md).

## 7. UI Bar (only when a UI was generated)
 
- [ ] 7.1 [`ui.md`](./ui.md)'s ask-step questions were actually asked, not assumed - style/brand, collection layout (table vs. cards/tiles vs. hybrid), overall UI shape, theme mode (light/dark/system), motion intensity, and (while the kit is AGPL) the license question - batched into one dialog, skipped only where the request or an already-answered question settles a given one, decided once before the first component was styled. ONLYOFFICE's UI kit is the always-on component/token foundation regardless of the answers; a named style re-themes its components, it never means bypassing or hand-rolling parallel ones. A file list built as a plain table when the layout question was answered "cards" or "hybrid" is the same class of miss as a wrong accent color - it just doesn't show up in a code diff the way a color does.
- [ ] 7.2 Every item in [`ui.md`](./ui.md)'s "The bar" is checked off individually - all five states per control, all three states per async region, no browser defaults left anywhere, the editor sized on its wrapper, phone width, motion, accessibility, real progress numbers, seeded real documents. When the archetype includes a sidebar, it is `position: fixed` (or full-height sticky), not a grid track that scrolls away. "Most of it looks fine" is not one of the checks.
- [ ] 7.3 The running app was opened in a real browser at a desktop width *and* a narrow one and looked at - screenshotted where the environment allows. This comes after §4.1-4.3, never instead of them.
- [ ] 7.4 When this deliverable has a file list/dashboard page, closing the editor actually returns to it: the cross button (`editorConfig.customization.close`, shown only when `onRequestClose` is declared) navigates there through `onRequestClose`, with no deprecated `goback.requestClose` in the config, checked by clicking it - not just wired in config and assumed to work because `destroyEditor()` runs without erroring. `destroyEditor()`/`window.close()` alone leaves the visitor on a blank or dead page, which is the same class of dead-end the thin-strip editor bug is, just one click later.
- [ ] 7.5 The generated CSS/JS is grepped for any selector or DOM lookup targeting the editor's placeholder element (the id/class passed to `new DocsAPI.DocEditor(...)`) anywhere other than that single constructor call - not just re-read and trusted, the same way 2.1/4.1 don't trust a read-through for reused assets. Init replaces that element with a sandboxed iframe and strips everything set on it (`api.md`); a leftover `#placeholder { width: ...; height: ...; }` rule left behind when a wrapper was added later does nothing *today* - a fixed-position wrapper can mask it completely - but it's exactly the rule this skill states three times over (here, `api.md`, [`ui.md`](./ui.md)) and it has still shipped anyway, which means recall alone isn't catching it. A grep for the placeholder's id/class outside that one line is cheap and catches it structurally instead.
- [ ] 7.6 Every popover-shaped element (row-action menu, combobox, tooltip, date picker) is actually opened - not just read - while nested inside whatever ancestor it really sits in (a horizontally-scrolling table is the recurring offender: `overflow-x: auto` alone still forces `overflow-y` to compute as `auto`, clipping vertically too). A `position: absolute` popover that is a plain CSS-positioned child of its trigger, instead of portaled to a top-level node and positioned from the trigger's own on-screen rect, is a defect the moment that ancestor's `overflow` isn't `visible` - see [`ui.md`](./ui.md)'s "The bar."
- [ ] 7.7 The rest/hover/selected (and any other adjacent-state) tokens for the same component are held next to each other and actually compared, not just checked for existing - two near-identical light tints (e.g. a hover gray and a selected blue-tint within a few points of lightness of each other) each pass in isolation and still leave "which state is this in?" unanswerable at a glance. See [`ui.md`](./ui.md)'s "Adjacent states are visually distinct from each other."
- [ ] 7.8 When the frontend target is React, Angular, or Vue, the editor is actually mounted through the official component ([React](https://api.onlyoffice.com/docs/docs-api/get-started/frontend-frameworks/react.md) / [Angular](https://api.onlyoffice.com/docs/docs-api/get-started/frontend-frameworks/angular.md) / [Vue](https://api.onlyoffice.com/docs/docs-api/get-started/frontend-frameworks/vue.md)) — grep the dependency manifest for the package and confirm the import is actually used, not just installed. The sibling `doceditor` skill's manual script-tag + `new DocsAPI.DocEditor(...)` pattern is a real finding here, not a stylistic preference, whenever the target is one of those three frameworks; it's correct only for a genuinely different framework (or an explicit request to avoid the dependency).
- [ ] 7.9 Every generated HTML/JS file is grepped for a `style="` attribute or a `<style>` block - not just spot-checked on the pages that were actively worked on last. Whenever a reverse proxy's CSP is in play (the normal case per [`infrastructure/nginx.md`](infrastructure/nginx.md)), any hit here is a shipped defect: the browser drops that inline style silently and logs a CSP violation, and the affected control renders in bare default browser styling - indistinguishable, on sight, from "this component was simply never styled." This is exactly the kind of miss 2.5 already checks for newly-added components generally; this item exists because it still shipped as an inline `style=` on an existing, already-styled page (a form input, a status badge) rather than as a whole unstyled component, which 2.5's phrasing doesn't clearly catch.

## 8. Caching
 
- [ ] 8.1 Reused static assets are version-busted (a query string keyed to server start time or a content hash) from the start of any project with a page, not added as an afterthought. Browsers cache CSS/JS far more aggressively than the HTML document on a plain reload - "the user says my fix didn't work" is frequently "the user's browser never re-fetched the fix," and this one change removes an entire class of false-negative debugging loops.
